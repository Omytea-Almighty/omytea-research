**How the English versions were made.** They were prepared on 2026-10-30, after all results in the report were known, and each was checked against its original by a second, internal reader (not external review). They keep the original's section numbering and translate every rule, threshold and number exactly. Two kinds of omission are distinguished. *Excerpts* (planning note, report notes, predictions) translate only the parts the report relies on; each says in its header what is left out. *Redactions* inside a translated part are marked in place as `[omitted: <category>]`, the categories being organisation or decision-maker reference, internal project name, internal tool name, internal administrative note, private file path, private document, and unpublished follow-up experiment; none removes a registered rule, threshold or result of the published experiments. Internal record identifiers that would not resolve publicly appear as `[internal record]` with a short description. Translator's notes are marked `[Translator's note: …]`. The Chinese originals remain the binding texts.

**Internal file names.** The English versions and the code comments refer to records by their internal file names. Their published versions: `DEVIATIONS.md` → `docs/deviations-D1-D16.en.md`; `THEORY-DRAFT.md` → `docs/theory-notes.en.md`; `PREDICTIONS-BEFORE-RESULTS.md` → `docs/predictions.en.md`; `runs/confirm/RESULTS-ADJUDICATION.md` → `docs/T1-results-adjudication.en.md`; `DIRECTION-CARD.md` → `docs/planning-note-excerpt.en.md`; `KT0-NOVELTY.md` → `docs/literature-search-record.en.md`; `REPORT-NOTES.md` → `docs/report-notes-excerpt.en.md`; `GATE-DIAGNOSIS.zh.md` → `docs/development-gate-diagnosis-summary.en.md`; the `.zh.md` pre-registrations and designs → the table above. `E3-RESULTS.zh.md` (an internal note on the E3 results, whose prediction reconciliation is translated in `docs/predictions.en.md`) and `PROGRESS.md` (an internal progress log) are not published. `GATE.md`, `STATUS.md`, `RESULTS.md` and `SUMMARY.md` are run outputs and are included under `runs/`.

**Checking a timestamp.** `openssl ts -reply -in <file>.tsr -text` prints the token time and the message imprint, which must equal the SHA-256 in the table. `openssl ts -verify -digest <sha256> -in <file>.tsr -CAfile <authority chain>` checks the signature. The `.ots` files can be checked with the OpenTimestamps client against the same digest; their Bitcoin block times are later upper bounds and are not used to order freezes against runs. The proofs for the E2 design and the E2.1 addendum contain only pending calendar attestations and no Bitcoin attestation; for those two documents the RFC 3161 tokens are the only timestamp evidence.

## 2. Code, run records and data (`repro/`)

`repro/` reproduces the layout the code expects: `experiments/open-system-world-model/` (code, tests, run records, report scripts, and in `data/` the E2 arm B category file), `data/` (third-party data; see `repro/data/README.md`) and `docs/timestamps/`.

**Software environment used:** Python 3.11.16, PyTorch 2.11.0, NumPy 2.4.4, SciPy 1.17.1, pandas 3.0.5, pyarrow 24.0.0, matplotlib 3.10.9, pytest 9.0.3. All computation ran on CPU. The T1 and E1 jobs ran with two threads each (the default of `src/osw/queue.py` and `src/osw/queue_e1.py`, also passed explicitly by `chain*.sh`; the probes set two threads in `probe*.sh`), and the E2 and E3 jobs with one thread (`chain5.sh`, `src/osw/run_e3.py`). The post hoc runs in `runs/e1-posthoc/` (written by `src/osw/run_e1_hmmtw.py`, whose docstring gives the command and which sets no thread count of its own) and `runs/e2-posthoc/` (no published command) did not record their thread count. Only the 410 E3 model-run records (not those in `runs/e3/c0/`) store the thread count. Thread count can change results at the level of floating-point summation order. All runs were made under macOS 15.8.2; the machine moved to macOS 27.2 on 2026-10-28, which changed the Accelerate LAPACK that PyTorch uses. Re-running published jobs under 27.2 during the internal review gave these differences: a T1 U1 job agreed within 4 × 10⁻¹² on the selected metrics; an E2 A1 HQ job and an E3 A1 HQ job agreed within 6 × 10⁻¹⁷; E2 HQ(3) differed by about 6 × 10⁻⁷ in per-horizon NLL and 4 × 10⁻⁴ in ECE; and E3 A2 HQ(3)-M seed 21 selected the same restart with CF within 1.8 × 10⁻⁵, but its moment loss (1.860 × 10⁻⁴ against 1.474 × 10⁻⁴) and moment-fit-only CF (0.8316 against 0.8410) moved. Treat eigendecomposition-dependent intermediate values as reproducible only within that OS and LAPACK version. `scripts/prep_aiwq.py` additionally needs xarray and the AI Weather Quest input files (see `repro/data/README.md`).

- **Code.** `src/osw/*.py` (28 files) is byte-identical to the timestamped E3 code manifest (`repro/docs/timestamps/2026-10-24-e3-design/E3-CODE-MANIFEST.json`). The v1.1 code manifest (`repro/docs/timestamps/2026-10-21-prereg-osw-v1.1/CODE-MANIFEST.sha256`) lists 98 files: 95 match the current tree, and the three files changed after the v1.1 freeze (`analyze.py` and `tests/test_analysis.py`, see deviations D13 and D14(e); and `queue_e1.py`, whose summary output was extended for E1, see report §3.6) are provided in their frozen form under `repro/frozen-v1.1/`, so the whole manifest can be checked. Because the code and run records are published unchanged, some internal strings remain: comments naming unpublished internal records (the Chinese design files such as `E3-DESIGN.zh.md`, and `DEVIATIONS.md`, `PREDICTIONS-BEFORE-RESULTS.md` and `PROGRESS.md`; see "Internal file names" in §1) and one naming the tool used in an internal review leg; labels of internal review findings (e.g. `r10 m3`, `review B4`) in comments and docstrings and in the `posthoc` field of the E1 post hoc records; a constant in `run.py` naming the private path of the v1.1 pre-registration (the runner records `null` when the file is absent); `scripts/prep_aiwq.py`, which refers to a private folder and virtual environment for its inputs; an internal bug-tracker identifier in `runs/chain2.log`; and the repository-relative paths inside the `.sha256` files of `repro/docs/timestamps/`.
- **Report scripts (`experiments/open-system-world-model/report/`).** `REPORT.md` and `numbers.json` (every result number taken from the run records, with its source), the figures, and the post hoc analysis scripts whose outputs the report uses (`param_audit.py`, `ident_audit.py`, `exact_ci.py`, `robustness.py`, `figures.py`, and three scripts added at release: `e3_coverage.py`, for the E3 interval coverage after the registered fallback; `post_review_checks.py`, for the H2 test comparison, the revival-index decomposition and C against L, L1 and K; and `rollout_diagnostics.py`, for the marginalised rollout and the return times of the published U2 checkpoints). These scripts are listed in `SHA256SUMS` but in neither timestamped code manifest; in the published copies of `param_audit.py` and `robustness.py`, comments that named internal review files, review legs or their finding labels were rewritten without changing any code. `check_k_representation.py` was written during an internal review; it is published here with its path setting and docstring adapted to this layout, and its output is `k-representability.json`. The script that renders `REPORT.md` from its template is not included.
- **Tests.** `experiments/open-system-world-model/tests/` covers T1, E1, E2 and E3. The E3 runner records the SHA-256 of `E3-DESIGN.zh.md` in every run and stops if the file is absent. To re-run E3 jobs or the E3 tests, place any file at `experiments/open-system-world-model/E3-DESIGN.zh.md`; the new records will then carry that file's hash instead of the original's, so they are distinguishable from the published ones. The E3 queue renames existing records whose design or code hash differs from the current one, so re-run E3 into a copy of the tree, not into the published `runs/e3/`.
- **Run records** (`experiments/open-system-world-model/runs/`): T1 (`dev`, `dev2`, `probe`, `confirm`), E1 (`e1`, `e1-posthoc`), E2 (`e2`, `e2-posthoc`), E3 (`e3`, including the E2-protocol subprocess records in `e3/c0`) and the outputs of the post hoc analysis scripts in `report/` (`robustness`), all byte-identical to the originals. Each of the 1,912 individual model-run records (one JSON file per trained or evaluated model) carries its own `result_sha256`; the summary, configuration, gate and manifest files, the `robustness` outputs, the model checkpoints in `runs/confirm/ckpt/`, and the logs and other run outputs carry no self-hash. All of them are listed in `SHA256SUMS`; `runs/TRAIN_CONFIG.json` and the whole of `runs/dev2/` (records, gate, status and queue log) are also listed in the timestamped v1.1 code manifest. The other provenance fields of the model-run records differ by experiment:

  | Records | Design or pre-registration hash | Code identity |
  |---|---|---|
  | T1 (`dev`, `dev2`, `probe`, `confirm`) | `prereg_sha256`, the v1 hash, written as a constant by the runner; the 450 `confirm` records also carry `prereg_v11_sha256`, computed from the v1.1 file at run time | `code_commit` (private repository); the timestamped v1.1 code manifest covers the confirmatory code |
  | E1 (`e1`, `e1-posthoc`) | `e1_design_sha256`, written as a constant by the runner | `code_commit` (private repository); the E1 runner and task code (`run_ethucy.py`, `tasks_ethucy.py`) are also listed in the timestamped v1.1 code manifest, and the published files match it; the `e1-posthoc` runner `run_e1_hmmtw.py` and the `models_e2.py` it imports are listed only in the later E3 manifest |
  | E2 (`e2`, `e2-posthoc`, `e3/c0`) | none | `code_commit` (private repository) only |
  | E3 (`e3`) | `design_sha256`, computed from the design file at run time | `code_manifest_sha256` (the timestamped E3 manifest) |

  The `code_commit` values name commits of the private repository and are not publicly resolvable. For E2 there is no timestamped code manifest from before its runs; its run-time code identity rests on those private commits (the same files are covered later by the E3 manifest). Not included: records of an unpublished follow-up experiment, one probe log that contains a local file path, a few console outputs, empty files, and the Chinese original of the T1 results adjudication (its English version is `docs/T1-results-adjudication.en.md`).
- **Known gaps.** The E3 development-gate records (`e3-DEV*`, `e3-FIX*`) were run under a pre-freeze draft of the design and code (hashes recorded in the records), which was not timestamped. The E2 arm B category file is included (`experiments/open-system-world-model/data/aiwq_tas_quintiles.npz`), but regenerating it from the raw weekly files needs an AI Weather Quest participant registration (see `repro/data/README.md`).

- **Erratum.** The module docstring of `src/osw/models_e2.py` says the T1 models "cannot represent observation-dependent Kraus operators". That is wrong about the T1 filter, which applies the instrument's observation-dependent Kraus operator after the model's dynamics; only the T1 blind rollout differs (report §1 and §5). It was the stated reason for not using the T1 models in E2, and no registered result depends on it. The file is left unchanged because it is hash-committed in the timestamped E3 code manifest.

`SHA256SUMS` lists every file in this supplement.
